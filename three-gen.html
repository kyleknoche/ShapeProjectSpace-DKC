Space Controls Three-Gen

Three generations between the platform and the application, and no more.

HTMLElement ↓ AbstractElement — Gen 1 ↓ TreeView — Gen 2 ↓ ShapeProjectTree — Gen 3

Dependency runs one way only: Gen 3 → Gen 2 → Gen 1 → HTMLElement.
Inspecting the classes…

This verdict is produced by walking prototype chains in your browser, not by reading a table.

Generation one is abstract and small. It establishes identity, the custom element lifecycle, ownership of the DOM an element creates, listeners that are guaranteed to be removable, and a single abstract action. It establishes nothing else, and the list of things it deliberately refuses is longer than the list of things it does.

Generation two is concrete and immediately useful. Fifteen ordinary controls that work with no application present: text entry, lists, trees, grids, forms, a panel, a meter. Every one of them could be dropped into an unrelated project this afternoon, which is the test that keeps them honest.

Generation three is authoritative. It is the only generation permitted to know that Shape Project Space exists, and it earns its position by binding rather than by re-implementing. A Gen-3 class that contains list rendering, tree flattening or validation logic is a Gen-3 class that has quietly become a second control library.

Because a base class that can be instantiated becomes a place to put things. The moment new AbstractElement() is legal, somebody will make one, hang behaviour on it, and the foundation will start growing features that only one caller needs.

So the constructor refuses two things. It refuses to build an AbstractElement directly, and it refuses to build any subclass that has not implemented the abstract action. The second refusal is the important one: it means that a Three-Gen element which does not know what acting means cannot come into existence at all.

if (new.target === AbstractElement)
{
    throw new TypeError("AbstractElement is abstract and cannot be instantiated directly.");
}

if (this.abstractAction === AbstractElement.prototype.abstractAction)
{
    throw new TypeError(new.target.name + " must implement abstractAction(); Gen 1 cannot know what acting means.");
}

Because an abstract middle layer has no way to prove it is useful. A concrete library can be opened in a browser, given data, clicked on, and found wanting. The control gallery registers Gen 2 and imports no application module at all; if that page still works, the boundary is real.

The rule that keeps the layer coherent is stricter than it first looks: a Gen-2 control may not import another Gen-2 control. Controls compose in a page, not inside each other. That is why Form has no import of Button and builds its own plain buttons, and why the two hierarchy controls share a plain model object rather than one inheriting from the other.

Because somewhere the software has to be about something. Project vocabulary, routes, content, graph topology and identity all have to live somewhere, and the discipline is to put all of it in one generation rather than letting it seep downwards one convenience at a time.

Seepage is the failure mode this pattern exists to prevent. It never arrives as a decision. It arrives as a Gen-2 control that gains one project-specific default, then a second, until the generic library is generic in name only.

Generation is computed as the number of inheritance steps from AbstractElement, not from the folder a file sits in. The abstract action column is obtained by constructing each control and asking it. Nothing in this table is written down twice.

An assistant that joins this repository tomorrow has no memory of why anything is the way it is. It has the files, and whatever the files can tell it. Everything it cannot infer, it will re-derive - and a re-derived architecture is a different architecture wearing the same names.

The generational boundaries turn that problem into a mechanical one. A file's folder says what it may depend on. A class's base says which generation it belongs to. A control's shape is set by fourteen siblings that already exist. When an agent is asked to add a control, the cheapest correct action is to copy the pattern in front of it, and the cheapest incorrect action fails a check before it is committed.

That is the whole claim: not that a model will understand the intent, but that the structure makes the intended move easier than the unintended one.

Nine things do the work, and none of them is a comment asking politely.

src/gen1, src/gen2, src/gen3. A file's location is its permission set.

Every project class begins with Shape. A generic control never does.

Generation is inheritance distance, so it cannot be claimed, only earned.

CODING-STANDARDS.md is short, absolute, and mostly about the DOM.

npm run check fails on a crossed boundary, generated markup or an anonymous listener.

The tests assert the pattern, not only the syntax: identity survives updates, listeners detach, reconnection works.

Fifteen controls written the same way are a stronger instruction than any paragraph.

docs/DECISIONS.md records why, so a later session argues with the reason rather than the result.

docs/HANDOFF.md is the current operational state, kept short enough to stay true.

Generation one can state that an element acts. It cannot state what acting means, because that is exactly the knowledge a concrete control adds. The public entry point is performAction(), which every gesture and every programmatic call routes through; the specialisation hook is abstractAction(), which every concrete class must implement.

The honest difficulty is that not every control has an obvious act. A meter mostly reports. The answer taken here was to give it a real one - acknowledge - rather than a ceremonial one, and to write the tension down in the decision record instead of hiding it.
